# Як працюємо

## Мова розробки — українська

Українська є робочою мовою проєкту. Це стосується всього, що пишеться для
людей: документації, коментарів у коді, повідомлень комітів, issues та
pull request'ів на GitHub.

Та сама конвенція діє в суміжному проєкті `sibling`, тож людина, яка
переходить між репозиторіями, не перемикає мову.

### Що якою мовою

| Що | Мова | Чому |
|---|---|---|
| README, `docs/`, `SECURITY.md`, цей файл | 🇺🇦 українська | документація для команди |
| Коментарі та docstring'и в коді | 🇺🇦 українська | пояснення *чому*, а не *що* — це текст для людини |
| Повідомлення комітів | 🇺🇦 українська | історія читається як розповідь про рішення |
| Issues, PR, code review | 🇺🇦 українська | обговорення |
| Імена змінних, функцій, класів, файлів | 🇬🇧 англійська | код мусить лишатись ідіоматичним |
| Поля API, колонки БД, назви змінних оточення | 🇬🇧 англійська | контракт із зовнішнім світом; перейменування = ламка сумісності |
| Тексти помилок в API (`detail`) | 🇬🇧 англійська | їх бачить клієнт, а не розробник |
| Рядки інтерфейсу застосунку | через i18n | див. нижче |
| Логи | 🇬🇧 англійська | їх грепають разом із бібліотечними |

Політика діє **на новий код і нові тексти**. Наявні англомовні коментарі
масово не перекладаються: така зміна зачепила б тисячі рядків, нічого не
покращивши, і заховала б справжні правки в шумі. Торкаєтесь ділянки — можете
дорогою перекласти її коментарі, але це не обов'язок.

**Російська не використовується ніде** — ані в коді, ані в документації, ані
серед мов інтерфейсу.

### Мова розробки ≠ мова продукту

Це різні речі, і їх легко переплутати.

*Мова розробки* — українська, вона для нас.

*Мова продукту* — це i18n у `apps/telegram-mini-app/src/i18n/`. Там
англійська стоїть як типова, бо аудиторія глобальна, і підтримуються
🇬🇧 English, 🇺🇦 Українська, 🇵🇱 Polski, 🇩🇪 Deutsch, 🇪🇸 Español. Локаль
визначається автоматично з Telegram.

Додаючи рядок в інтерфейс, додайте його в **усі п'ять** словників —
`translations.ts` типізований, тож TypeScript не дасть забути.

## Коміти

Формат вільний, але змістовний. Один коміт — одна завершена зміна.

Що має бути в повідомленні:

* **що змінилось** — у першому рядку, до 72 символів;
* **чому** — в тілі, якщо причина не очевидна з діфу;
* **як перевірено** — коли виправляється баг.

Опис *чому* цінніший за опис *що*: що змінилось, видно з діфу, а чому — ні.

```
Закрити 500 на дублікаті гаманця

solana_wallet має UNIQUE-констрейнт, а ендпоінт писав у нього без обробки
конфлікту — друга спроба прив'язати ту саму адресу давала неопрацьований
IntegrityError замість 409.

Перевірено: tests/test_wallet.py, 11 тестів.
```

Історія приватного репозиторію squash'иться в один коміт під час публікації
дзеркала, тож інфраструктурні деталі в повідомленнях назовні не потраплять —
але це не привід писати їх недбало.

## Код

* Коментар пояснює **причину рішення**, а не переказує наступний рядок.
* Якщо щось зроблено не найочевиднішим способом — напишіть чому саме так,
  інакше наступний розробник (або ви за місяць) це «спростить» назад.
* Симуляцію треба називати симуляцією. Класи `Mock*` повертають
  `example.invalid`, а рядки NFT мають `is_onchain=false` — так результат
  неможливо сплутати зі справжнім.

## Тести

Виправлення бага супроводжується тестом, який **падав би до виправлення**.

`backend/tests/test_security.py` — регресії на обхід автентифікації та
економіки. Червоний тест там блокує реліз, без винятків.

```powershell
cd backend; python -m pytest        # 57 тестів
cd apps\telegram-mini-app; npx tsc --noEmit; npm run build
```
